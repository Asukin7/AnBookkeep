## 三、高优先级问题

### 3.1 图片识别取消链路不完整

当前取消令牌主要传递给在线 AI 请求，图片预处理和 PaddleOCR 本地识别阶段不能立即停止。用户在本地 OCR 阶段取消单张识别或离开批量识别页面后，后台任务仍可能继续运行。

可能影响：

- 临时图片需要等待定时清理。
- 后续 OCR 请求可能等待前一个已取消任务结束。
- 页面已经销毁后，识别结果无人接收。
- 取消操作的实际行为与用户预期不完全一致。

计划：

- 建立统一的识别取消上下文，而不是只依赖 Dio `CancelToken`。
- 在预处理完成、OCR 前后、AI 请求前后增加协作式取消检查。
- 无论页面是否仍存在，都在取消和异常路径释放临时图片。
- 防止单张识别重试被重复触发。
- PaddleOCR 当前无法中断正在执行的原生推理时，明确区分“已请求取消”和“底层推理已结束”，避免继续合并和展示结果。

### 3.2 日期范围不统一

当前不同模块使用了不同日期范围：

- 明细和分析年份滚轮默认支持 2020 年至当前年。
- 新增记账和搜索日期组件支持 2000 年至 2100 年。
- 文件导入可接受更宽的四位年份范围。

这会导致账单能够被保存或导入，但无法通过明细或分析的时间选择器定位。

计划：

- 抽取统一的日期策略和值校验。
- 正常选择范围继续保持原需求中的 2020 年至当前年。
- 当数据库实际存在范围外账单时，明细和分析年份滚轮自动扩展到实际最早、最晚数据年份。
- 新建、编辑、搜索和导入统一使用相同的合法日期校验。
- 增加范围边界、闰年、范围外导入和编辑账单测试。

### 3.3 搜索与分析页面可能保留旧数据

外部分享图片记账完成后会发送账本变更通知，目前明细页面会监听并刷新，搜索和分析页面没有接入同一刷新机制。

计划：

- 把账本变更通知收敛为统一的数据失效机制。
- 明细、搜索和分析页面根据自身筛选条件刷新，不重复实现通知判断。
- 防止相同一次保存引起重复查询或刷新抖动。
- 增加在搜索页、分析页上方完成分享记账后的回归测试。

### 3.4 XLSX 导入存在异常内存峰值风险

文件大小限制只能限制压缩文件本身，XLSX 的行数和内容限制需要在解压、解析后才能得知。异常压缩率文件可能在解析前占用大量内存。

计划：

- 在 XLSX 完整解析前检查 ZIP 条目数量、单条目解压大小和总解压大小。
- 为工作表数量、列数、单元格文本长度和有效行数增加明确上限。
- 避免当前外层 Isolate 与 `decodeBytesAsync` 内层 Isolate 的重复调度。
- 对超限、损坏和加密文件返回统一的用户提示。

## 四、中优先级问题与优化点

### 4.1 大数据导出

当前会一次性读取全部账单并在 UI Isolate 创建完整 XLSX 工作簿。编码压缩虽然在后台执行，但大量单元格创建仍可能导致界面卡顿和较高内存峰值。

计划：

- 将 XLSX 工作簿创建和编码整体移入后台 Isolate。
- 数据库按页读取，避免同时保留多份完整中间列表。
- CSV 优先采用临时文件流式写入。
- 明确单次导出的安全数据量，并为超大导出提供可理解的提示。

### 4.2 批量图片识别重复加载上下文

每张图片都会重新读取 API Key、AI 配置、提示词和分类数据。批量选择 20 张图片时会产生重复安全存储与数据库访问。

计划：

- 创建批次级 `RecognitionContext`。
- 一个批次只加载一次 AI 配置、API Key、活动提示词和分类快照。
- 单张识别继续复用同一识别管线。
- 配置在批次开始后变化时，下一批次再生效，保证同批数据一致。

### 4.3 图片、OCR 与 AI 请求边界

当前缺少对压缩后图片字节数、图片像素尺寸、OCR 原文长度、分类提示文本长度和最终提示词长度的统一上限。

计划：

- 在 Android 分享入口和 Flutter 图片预处理层同时校验文件类型、尺寸和像素数量。
- 限制压缩结果字节数，超限时进一步降采样或提示用户。
- 限制 OCR 原文与最终提示词长度，并记录截断指标，不在 Release 日志中记录敏感正文。
- 对批量图片数量进行 Flutter 侧二次校验。

### 4.4 历史备注查询

每次打开历史备注面板都会扫描并聚合全部带备注的账单，再在 Dart 层计算排序。数据量增大后成本会持续上升。

计划：

- 先在 SQL 层筛选有价值的候选备注。
- 根据使用次数、最近使用时间和智能评分需要保留合理候选集，再取前 20 项。
- 评估是否增加备注统计表；若普通 SQL 优化已经满足性能要求，则不增加额外表和同步复杂度。

### 4.5 相同时间账单排序稳定性

批量创建和导入时多条账单可能拥有相同的账单时间和创建时间，当前排序缺少最终稳定字段，重载后相同时间账单的内部顺序可能变化。

计划：

- 为所有账单查询增加一致的最终排序键。
- 保持“账单时间倒序、创建时间倒序”的现有业务规则。
- 增加同一分钟、同批次账单的稳定排序测试。

### 4.6 错误信息边界

分析页和路由错误页存在直接展示底层异常文本的情况。通用错误转换也把所有 `FormatException`、`ArgumentError` 和 `StateError` 默认视为可直接显示，第三方库异常可能携带实现细节。

计划：

- 仅允许实现 `UserFacingException` 的业务错误直接显示。
- 为文件、数据库、网络和配置错误分别映射稳定文案。
- 内部详情只进入脱敏日志。
- 错误页面提供返回或重试操作。

### 4.7 搜索查询压力

搜索已经具备 180 ms 防抖和代次失效保护，但每次有效输入仍会查询最新匹配月份并重新加载整年结果。旧数据库查询不能真正取消。

计划：

- 保留输入自动刷新的现有交互。
- 合并“定位最新年份”和“加载首年结果”的查询。
- 只有查询条件真实变化时创建新搜索任务。
- 对金额输入错误明确标记结果处于旧条件状态，避免用户误判。
- 使用大数据集验证连续输入期间的帧稳定性和查询次数。

### 4.8 控件内部尺寸

`AppSegmentedButton` 的内容高度和外层高度存在重复约束，顶栏中的实例会被父级压缩为另一套实际高度。

计划：

- 明确普通和顶栏紧凑两种规格。
- 统一由尺寸令牌控制总高度、内边距和选中卡片圆角。
- 保持当前页面布局、视觉尺寸和四角圆角效果不变。

## 五、代码结构优化

当前较大的源码文件包括：

- `analytics_page.dart`：约 1045 行。
- `detail_page.dart`：约 767 行。
- `bookkeeping_page.dart`：约 755 行。

- `search_page.dart`：约 581 行。

计划按照职责拆分，不为了缩短文件而机械拆分：

### 5.1 页面层

- 分离状态协调器与纯展示组件。
- 分析页拆分筛选、汇总卡片、趋势图、分类图和图表格式化逻辑。
- 明细页拆分快捷记账控制、月份选择和加载协调。
- 记账页拆分表单状态、历史备注、计算器显示与键盘。
- 批量识别页拆分任务控制器、项目卡片和图片预览。
- 搜索页拆分条件控制器、筛选面板和分页协调。

### 5.2 数据层

- 将分类、账单、历史备注查询从单一 `BookkeepingRepository` 中按职责组织。
- 公共查询条件、日期范围和排序规则只定义一次。
- 保持页面不直接访问 Drift 表或拼接 SQL。

### 5.3 公共能力

- 抽取统一异步错误状态和 SnackBar 展示入口。
- 统一日期策略、数据失效通知、后台任务取消和文件安全限制。
- 删除已经没有生产调用的旧纯逻辑及重复局部常量。
